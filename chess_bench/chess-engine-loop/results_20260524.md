# Chess Engine Generation Benchmark Report — 2026-05-24

## Scope

This benchmark asks Codex models to create a Python UCI chess engine from scratch, then evaluates the generated `engine.py` against Stockfish.

Candidate constraints:

- Final candidate artifact is `engine.py`.
- Candidate must implement enough UCI to play games.
- Candidate may use only the Python standard library.
- Candidate prompt forbids inspecting/copying/adapting Stockfish, commercial engines, python-chess, Sunfish, TSCP, or other chess engine/library source.
- Static checks reject Stockfish mentions, `import chess`, python-chess mentions, and known engine-source markers.

Stockfish is used only as opponent/evaluator.

## Evaluation Setup

- Candidate model/effort: `gpt-5.4-mini low`, `gpt-5.5 low`.
- Stockfish reference: local extracted binary at `tmp/stockfish_local/root/usr/games/stockfish`.
- Stockfish strength: `UCI_Elo=1320`, depth `1`.
- Candidate per move: `go movetime 20`.
- Max plies per game: `40`.
- Games per result row: `16`.
- Elo estimate: Jeffreys-smoothed W/D/L score against reference Elo 1320.

Chess benchmark suites:

- `opening_gauntlet`: 4 opening FENs, both candidate colors.
- `advantage_conversion`: 4 advantage/conversion FENs, both candidate colors.

This satisfies the “minimum 2 chess benchmark problems/suites” requirement; each suite contains multiple positions.

## Compared Structures

- `one_shot`: model writes one engine; hidden evaluator scores it.
- `hidden_eval_loop`: round 2 receives only public score feedback from hidden evaluator; no previous engine code.
- `cumulative_hidden_eval_loop`: round 2 receives public score feedback plus previous engine code.
- `solver_visible_public_eval`: solver receives previous engine code and a visible `public_eval.py` smoke scorer; hidden evaluator still produces the reported score.

## Interpretation

The benchmark works and is discriminative. It exposes illegal move failures, UCI/timeout failures, round-to-round changes, and scorer visibility effects.

The strongest structure by mean best Elo is `cumulative_hidden_eval_loop` for both models:

- `gpt-5.4-mini`: mean best 1115, best 1215.
- `gpt-5.5`: mean best 1129, best 1143.

So at the coarse structure level, the best structure on `5.4-mini` does transfer to `5.5`: cumulative previous-code feedback is the top mode for both. However, the round behavior does not transfer cleanly:

- `gpt-5.4-mini` cumulative r2 is volatile: one trial dropped to 838, the other rose to 1215.
- `gpt-5.5` cumulative r1 is consistently strong, but r2 degraded in both trials: 1115 -> 970 and 1143 -> 838.

This suggests that cumulative code helps find strong initial structures, but repeated editing can entrench or damage weak implementation choices.

`gpt-5.5 low` is not automatically better in every structure:

- It beats `5.4-mini` on mean best for `one_shot`, `hidden_eval_loop`, and `cumulative_hidden_eval_loop`.
- It loses to `5.4-mini` on the best observed single result because `5.4-mini cumulative r2` reached 1215.
- It has more timeout/completion risk in `one_shot` and especially `solver_visible_public_eval`.

Visible public scorer access did not reliably help:

- `gpt-5.4-mini solver_visible_public_eval`: mean best 899, highly unstable, with one good recovery trial and one unrecovered illegal-move trial.
- `gpt-5.5 solver_visible_public_eval`: mean best 942, lower than its hidden-feedback and cumulative modes, with repeated generation timeouts.

In this setup, evaluator-owned feedback is cleaner and cheaper than solver-visible public scoring. Solver-visible scoring can produce a rescue in one run, but it increases wall-clock time and does not reliably improve hidden Elo.

## Conclusion

Current answer to the user's main question:

- A loop that works on `5.4-mini` can transfer to `5.5`, but the improvement is not monotonic and not guaranteed.
- The best observed structure, cumulative previous-code feedback, is best for both models by mean best Elo.
- Bigger model + same loop is usually stronger here, but low-effort timeout behavior can erase that advantage.
- Repeated/cumulative rounds are not automatically a convergence process; they can improve sharply or regress sharply.
- Solver-visible scorer access is not clearly beneficial in this chess-engine benchmark; hidden evaluator feedback plus selective cumulative code reuse is the better current structure.

## Caveats

- Two trials per condition are enough to show direction and instability, not enough for precise Elo.
- Each row is only 16 games; Elo values should be read as noisy structure-comparison scores.
- The Stockfish reference is deliberately weak and fast to keep model-generation experiments practical.
