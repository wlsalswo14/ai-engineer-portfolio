# Primus v2

Primus는 **AI가 일하는 방법 자체를 실험해서 더 좋은 방법으로 교체하는 시스템**입니다.

예를 들어 코딩 답 하나를 잘 만드는 것이 목적이 아니라, 다음과 같은 작업 순서를 비교합니다.

- 바로 답 만들기
- 먼저 요구사항을 정리한 뒤 답 만들기
- 초안을 만든 뒤 별도 검토자가 고치기

여기서 작업 순서를 `Harness(작업법)`이라고 부르고, 실제 엔진·코드·답은 `Artifact(결과물)`이라고 부릅니다.

## 왜 이제 더 범용적인가

예전 구조는 Chess, Cache, Coding, Reasoning 네 가지를 본체 코드에 직접 연결한 **네 칸짜리 전용 자판기**에 가까웠습니다. 새 분야를 넣으려면 자판기 본체를 뜯어야 했습니다.

지금은 공통 슬롯 규격이 있습니다. 새 분야는 다음 네 가지만 준비하면 됩니다.

1. `config/domains/<새분야>.json`
2. `module:Class` 형태의 평가 어댑터
3. 서로 겹치지 않는 공개/비공개 문제 세트
4. 최초 작업법과 기준 결과물

핵심 오케스트레이터, CLI, 상태 조회, 무결성 검사는 설정의 도메인 목록을 자동으로 읽습니다. 즉, **분야는 바뀌어도 개선 절차는 그대로 재사용**됩니다. 이것이 여기서 말하는 “범용적”의 뜻입니다.

## 새 개선 루프

```text
       공개 실험 노트
  (무엇을 바꿨고 왜 실패했나)
              |
              v
      증상에 맞는 탐색 선택
  (추가/삭제/교체/재조합/새 설계)
              |
              v
       후보 작업법 1~3개 생성
              |
              v
       작은 공개 문제로 예선
              |
              v
          후보 하나 선택
              |
              v
  현 챔피언 vs 후보 공개 정식 비교
       |                    |
     탈락          공개 결과물 미리 봉인
                            |
                            v
          의미상 새 문제인 비공개 본시험
                (후보 하나만 응시)
                    |               |
                  탈락            통과
                                    |
                                    v
                         작업법을 원자적으로 승격
                                    |
                   +----------------+----------------+
                   |                                 |
           domain_lineage                     task_local
        공개에서 고른 결과물도 승격       작업법만 승격, 답은 과제마다 새로 생성
```

현재 공개 예선 후보 수는 비용에 맞춰 다릅니다.

- Chess: 1개 — 한 번의 평가가 100게임이라 예선 후보를 늘리지 않음
- Cache: 2개
- Coding: 3개
- Reasoning/Tools: 3개

## 각 개선이 왜 좋은가

### 작업법과 결과물을 분리

`fib()` 정답 코드는 다음 `toposort()` 문제의 정답이 아닙니다. 하지만 “요구사항 확인 → 구현 → 검토”라는 작업법은 둘 다에 쓸 수 있습니다.

- Chess/Cache는 같은 엔진·정책이 다음 라운드에도 이어지므로 `domain_lineage`입니다.
- Coding/Reasoning은 매번 문제가 달라지므로 `task_local`입니다. 특정 문제의 답을 챔피언처럼 물려주지 않고 작업법만 승격합니다.

요리로 비유하면, 서로 다른 주문에 지난번 완성 음식을 넘기는 대신 **더 좋아진 레시피와 주방 동선**을 넘기는 것입니다.

### 여러 후보를 공개 예선에서 비교

아이디어 하나만 매번 본시험에 보내면 운 나쁜 아이디어에 비공개 문제를 낭비합니다. 그래서 값싼 공개 문제에서 서로 다른 후보를 먼저 비교한 뒤 하나만 본시험에 보냅니다.

채용으로 비유하면 지원자 세 명에게 공개 과제를 주고, 그중 한 명만 비공개 최종 면접에 보내는 방식입니다.

### 비공개 문제는 이름이 아니라 내용으로 1회 사용

예전에는 같은 문제를 `secret-01`에서 `secret-02`로 이름만 바꾸면 새 문제처럼 보일 수 있었습니다. 지금은 평가에 실제 영향을 주는 문제 내용, 고정 데이터 해시, 실행 조건을 묶어 지문처럼 계산합니다.

시험지 표지만 바꿔도 문제 내용이 같으면 같은 시험입니다. 이미 쓴 비공개 묶음이면 라운드를 시작하기 전에 중단하므로 비싼 후보 생성 비용도 낭비하지 않습니다.

### 실패 목록 대신 실험 노트

단순히 “실패함”만 저장하면 다음 설계자가 같은 실수를 다른 이름으로 반복합니다. 지금은 공개 결과만 사용해 다음을 기록합니다.

- 어떤 구조 요소를 바꿨는가
- 왜 좋아질 것으로 예상했는가
- 지켜야 할 기존 장점은 무엇인가
- 공개 비교에서 이김/짐/동률이 어땠는가
- 품질과 비용 방향은 어땠는가
- 어떤 실패 유형이 반복됐는가

비공개 점수와 정답은 이 노트에 들어가지 않습니다.

### 고정 순환 대신 증상에 맞는 탐색

항상 `추가 → 삭제 → 교체`를 기계적으로 반복하지 않습니다.

- 비용·시간 초과가 반복되면 먼저 `delete`
- 형식·계약 위반이면 `replace`
- 품질 퇴보면 `recombine` 또는 `de_novo`
- 일정 주기마다 연구 전이 같은 먼 탐색

감기에 무조건 같은 약을 주는 대신 증상에 맞춰 다음 검사를 고르는 것과 같습니다.

### 0점/1점만 보지 않는 평가

코딩 테스트 10개 중 7개 통과는 “형식 자체가 망가진 제출”과 다릅니다. 이제 일반 테스트 실패나 오답은 유효한 0~1 품질 신호로 기록하고, 금지 도구 사용·보호 파일 변경 같은 계약 위반만 무효 처리합니다.

또한 품질이 떨어지지 않으면서 비용이 충분히 줄면 효율 개선으로 승격할 수 있습니다. 품질과 비용을 한 숫자로 억지로 섞지 않고 각각 확인합니다.

## 실행

cd C:\Users\jinminjae\OneDrive\Desktop\RSI\primus

```powershell
python -m primus.cli loop resume coding
```

## 중요한 위치

- 도메인 설정: `config/domains/`
- 공개/비공개 문제: `config/tasksets/`
- 공개 실험 노트: `resources/public_lessons/<domain>/`
- 공개 행동 피드백: `resources/public_audits/<domain>/`
- 활성 챔피언 포인터: `registry/domains/<domain>/active.json`
- 동결된 외부 채점기: `src/primus/vendor/`(해시는 `VENDOR.json`, 검증은 `primus doctor`)
- 변경 불가능한 객체/영수증: `objects/sha256/`, `receipts/sha256/`
- 라운드 증거: `runs/<domain>/<run-id>/`
- 상태 DB: `state/primus.db`

세부 규칙은 [Architecture](docs/ARCHITECTURE.md), [Evaluation Protocol v2](docs/EVALUATION_PROTOCOL_V2.md), [Operations](docs/OPERATIONS.md)에 있습니다.
